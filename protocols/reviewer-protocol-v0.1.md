# Shirakami Reviewer Protocol v0.1

## Purpose

The Reviewer Protocol provides an executable entry path for people who want to inspect, test, and evaluate the Shirakami Project.

It is not an evaluation engine and does not replace reviewer judgment.

The protocol is designed so that a reviewer can experience Shirakami through its own operating principles rather than relying only on explanatory documentation.

> AI is a simulator, not an authority.

## Core Pipeline

```text
Reviewer Entry
      ↓
Landscape
      ↓
Evidence
      ↓
Protocol
      ↓
Runtime
      ↓
Verification
      ↓
Human Gate
      ↓
Review Evidence
```

## 1. Reviewer Entry

The reviewer enters through the project-level protocol rather than through an application-specific interface.

The entry point should identify:

- the repository or component under review
- the current version / commit
- the stated purpose
- the expected runtime entry point
- the available verification method

## 2. Landscape

Collect the context necessary to understand what is being reviewed.

Landscape may include:

- project README and specification
- repository structure
- relevant Protocol definitions
- Runtime implementation
- tests and verification artifacts
- current development status

Landscape is context, not Evidence by itself.

## 3. Evidence

Separate observable or source-backed information from interpretation.

Evidence should identify, where applicable:

- source
- evidence_id
- version or commit
- observation
- provenance
- verification status

Unverified assumptions must not be silently promoted to Evidence.

## 4. Protocol

Translate the review objective into an explicit executable procedure.

The reviewer should be able to inspect the procedure before execution.

The protocol must state:

- what will be executed
- what is expected
- what will be observed
- what constitutes verification
- where human judgment remains necessary

## 5. Runtime

Execute the specified procedure against the selected implementation.

Runtime output is an observation. It is not automatically a fact, conclusion, or approval.

Provider-specific AI behavior must remain distinguishable from Shirakami protocol behavior.

## 6. Verification

Compare Runtime observations with the stated protocol and expected conditions.

Verification should answer:

- Did the specified procedure execute?
- What was actually observed?
- Which Evidence supports the observation?
- Were there deviations or failures?
- Which claims remain unverified?

## 7. Human Gate

The final evaluation remains with the reviewer.

Shirakami must not:

- make the reviewer's final judgment
- convert an inference into Evidence
- hide missing Evidence
- present an unverified result as verified
- pressure the reviewer toward approval or rejection

The protocol should instead expose the information required for independent judgment.

## 8. Review Evidence

The review process itself may produce Evidence.

A review record should preserve, where practical:

```yaml
review:
  protocol: "Shirakami Reviewer Protocol v0.1"
  target:
    repository: "..."
    commit: "..."
  evidence_ids: []
  runtime_observations: []
  verification_results: []
  unresolved_questions: []
  reviewer_judgment: "human-controlled"
```

The reviewer judgment is intentionally not generated by the protocol.

## Non-Goals

This protocol does not:

- certify the Shirakami Project
- rank the project against other systems
- replace independent technical review
- claim that successful execution proves the underlying theory
- treat AI-generated explanations as authoritative evidence

## Relationship to the Shirakami Project Protocol

The Reviewer Protocol is a project-level protocol layered over the existing Shirakami architecture.

```text
Shirakami Project Protocol
│
├─ Core Runtime Protocol
├─ Evidence Protocol
├─ Semantic Handoff Protocol
└─ Reviewer Protocol
```

The Reviewer Protocol therefore acts as the public inspection boundary of the project.

## Design Principle

A reviewer should not have to believe Shirakami in order to review Shirakami.

The project should expose enough of its Landscape, Evidence, Protocol, Runtime, and Verification path for the reviewer to make an independent judgment.
